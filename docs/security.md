# Security

What Premier protects, how, and where it stops. Read the limits before you rely on it.

## What Premier protects

**Confidential paths.** A person who may not read a file does not receive it. Not its contents, not its name, not its Git object ID. This holds for signed-in members and for anonymous clones.

**Confidential branches.** A person who may not see a branch is not told it exists, and cannot fetch its commits even if they know a commit ID.

**Secrets, against agents.** An agent session never holds a secret's value. It holds a placeholder. The value is added to an outgoing request by a proxy outside the agent's process, and only for the hosts, methods and paths the secret's schema allows.

**External MCP tools, against agents and upstream drift.** Through the Policy-Unified MCP Action Gateway (`premier mcp gateway` and `/v1/mcp/rpc`), MCP tools are default-deny, narrowed to `permissions(human) ∩ permissions(agent_profile)`, checked against argument guardrails and SHA-256/TOFU tool-definition pins, injected with credentials host-side (`use ≠ read`), and scrubbed for reflected secrets before results reach the agent.

**The repository, against agents.** An agent session works on a private copy that holds only what its identity may read. In the sandbox it has no network but its own proxy and cannot see the repository at all; what it changed in its copy is committed only when an owner asks.

**The server's own files, against pushed content.** With a state directory, accounts, vaults, keys and audit logs are not in any repository's working tree, so nothing that is pushed can be checked out over them.

**Accounts.** Passwords are hashed with argon2id. Access tokens and recovery codes are stored as hashes. Two-factor codes cannot be replayed. Failed sign-ins are rate-limited per address.

## How

**Projection on the server.** The full history lives only on the server. For each caller, the server builds a filtered copy of the history: the branches they may see, with the files they may not read removed from every commit. Git clients talk to that copy. Nothing is filtered on the client, so a modified client gains nothing.

**Objects are scoped to the caller.** A fetch can only ask for objects that are part of the caller's own projection. Asking for the ID of a hidden commit or file gets the same answer as asking for one that does not exist.

**One policy, evaluated the same way everywhere.** The Studio's file tree, file contents, search, blame, Git fetch and Git push all ask the same compiled policy the same question. Deny overrides allow, and the server policy overrides the repository's.

**Pushes are checked path by path.** A push is accepted only if the pusher has `write` on every path it adds, changes or deletes, on a branch they can see. The server then puts the hidden files back into the commit it stores. Rejections that depend on something the pusher cannot see all read the same.

**Every change is a commit.** A file saved or deleted in the Studio is one commit on its branch, authored by the signed-in account and checked against the same policy as a push. The server keeps no uncommitted edits.

**The policy is read from history, and guarded.** The server enforces the `.access.toml` committed at the tip of the default branch, and reads `.env.schema` from the same place. A change to either file there, whether it arrives by push, Studio edit, publish or a committed agent session, is accepted only from an owner, and only if the new policy parses, compiles under the server policy and leaves the group `owners` able to read and write `.access.toml`. Anyone else gets the generic rejection.

**Publish cannot overwrite.** Publishing a branch lands its changes since it forked from the target as one commit on top of the target, without the paths the public may not read. Non-overlapping edits to the same regular text file merge cleanly via 3-way line-level merge (and the merged result is checked against private blobs); overlapping edits, mode or delete collisions, and binary conflicts refuse the whole publish. Everything else on the target stays as it was.

**State is outside the working tree.** Started with `--state-dir` (the image sets it), the server writes nothing of its own into a repository's directory. Three more things hold either way. A path with a component named `.premier`, `.premier-local` or `.git`, or any spelling a case-insensitive, NTFS or HFS+ filesystem treats as one, is refused in pushes, publishes, Studio edits and agent-session commits. The server updates a working copy only when a state directory is in use, the copy had no local changes, the new commit names no such component and it writes over no file Git ignores. And state found in a working tree is moved into an empty state directory once, never merged into one that has state.

**Agent sessions are caged.** A session gets a workspace written from its identity's projection of one branch: the owner who started it, narrowed by the agent profile. It is outside every repository, in an owner-only directory. On Linux it runs in bubblewrap. The sandbox's filesystem is an allow-list: `/usr`, `/bin`, `/sbin`, `/lib`, `/lib64`, `/etc/ssl`, `/etc/ca-certificates` and `/etc/alternatives` read-only, a generated `/etc/passwd` and `/etc/group`, the workspace, and nothing else of the host. It has its own process IDs and no network except a relay to the session's own proxy. The server computes what changed by reading the workspace itself, never by running Git in it and never through a symbolic link, checks sizes before it reads, and commits the result only when an owner asks, with `write` checked for the session's identity on every path.

**MCP tool calls go through a policy-unified gateway.** Upstream `[mcp_servers.<name>]` servers are default-deny: a tool is exposed or callable only when `[[mcp_rules]]` allow it (with Deny overriding Allow and the server policy overriding the repository's) and, when an agent profile is active, `permissions(human) ∩ permissions(agent_profile)` (`allow_mcp_tools` minus `deny_mcp_tools`) also allows it. Caller identity is bound at startup (`premier mcp gateway`) or taken from the authenticated server session (`/v1/mcp/rpc`); identity-override arguments in tool calls are rejected. Credentials bound to an MCP server must be permitted for that server in `.env.schema` (`mcp_servers`, plus `egress.hosts` for `http_sse` upstreams) and authorized for `use`, are injected host-side (cleared child environment for `stdio`, TLS request headers for `http_sse`), and are scrubbed (raw, percent-, hex-, JSON- and base64-encoded) from tool descriptions, call results and error messages while `premier_cap_v1_*` placeholders are refused in external tool arguments. Before listing or calling any tool—including direct `tools/call` requests that skipped `tools/list`—the gateway hashes the canonical tool definition and checks it against `pinned_tool_hashes`, prompt-injection/hidden-Unicode heuristics and TOFU pins, quarantining any mismatch or drift. Remote `http_sse` upstreams require HTTPS by default, refuse compressed responses, and resolve and vet every DNS answer against loopback, link-local/metadata (`169.254.169.254`), broadcast, multicast and private/CGNAT/ULA ranges before dialing the vetted IP directly.

**Autonomy budgets and resource caps.** `[[agent_profiles]]` in `.access.toml` (tightened by server policy) can declare per-session blast-radius and anomaly limits (`max_files_modified`, `max_lines_changed`, `max_workspace_bytes`, `max_egress_requests`, `max_egress_bytes`, `max_jit_requests`, `max_denied_attempts`), OS resource caps (`max_memory_mb`, `max_pids`, `max_cpu_secs`), and `on_budget_exceeded = "pause" | "terminate"`. The egress proxy checks request and JIT budgets before forwarding or queueing and meters `CONNECT` passthrough tunnels chunk-by-chunk (severing connections immediately on breach), the session runner scans workspace deltas continuously against workspace caps, and Linux sessions apply `setrlimit` (`RLIMIT_AS`, `RLIMIT_CPU`) plus cgroup v2 (`memory.max`, `pids.max`; UID-global `RLIMIT_NPROC` is not used). Breaches emit `AuditDecision::BudgetExceeded` and live SSE `budget_alert` events (filtered by owner or session principal): `terminate` returns `403` and kills the child, while `pause` returns `429`, freezes the process tree via cgroup v2 `cgroup.freeze` on Linux (falling back to terminating `bwrap --new-session` sessions if writable cgroup v2 is unavailable, `-pgid` `SIGSTOP` on unsandboxed Unix hosts, or proxy-only gating off Unix), and parks until an owner raises the budget and resumes (`POST /v1/agents/sessions/{id}/budget`) or stops it.

**Envelope KMS, external connectors, and Key Transparency.** Secrets can be encrypted under AES-256-GCM per-vault DEKs wrapped by a separated KEK (`PREMIER_KMS_KEY`, `PREMIER_KMS_URI` which refuses `file://` keys inside the state directory, or HashiCorp Vault Transit over verified TLS) with optional read-through fallbacks from Vault KV v2 or 1Password Connect (namespaced strictly by `{repo_id}/{layer}/{scope}/{var_name}`), or kept in sovereign `age` + AEAD mode. Owners can migrate sovereign vaults to Envelope KMS and rotate DEKs in place (`POST /v1/secrets/kms/migrate`, `POST /v1/secrets/kms/rotate-dek`); migration verifies every migrated entry before committing, deletes the retired `vault.toml` (plus `age.key` when the KEK is external), and logs `migrate_retire_age`, while configuring an external KEK over an un-migrated `vault.toml` fails closed until migrated. Both modes bind vault recipients/key identifiers into an append-only SHA-256 hash-chained Key Transparency log (`key_transparency.jsonl`) that fails closed on silent public-key swaps, log tampering, or missing/emptied KT logs on bound vaults.

**Keyless OIDC workload identity, dual-phase rotation, and offboarding kill-switch.** The control plane issues short-lived (default 5 min, max 1 h) workload assertions signed with EdDSA (Ed25519) (`sub` plus RFC 8693 `act` for delegated agents, scoped strictly to `human ∩ agent_profile`). Relying parties verify them asymmetrically against the public keys at `/.well-known/jwks.json`, so no shared secret leaves the server; OIDC discovery at `/.well-known/openid-configuration` advertises the JWKS and `/v1/oidc/token`, and timestamped revocations in `oidc_revoked.json` keep pre-revocation tokens invalid even after re-enablement while allowing newly minted tokens). Variables declaring `[vars.X.rotation]` rotate via HMAC-SHA256 signed dual-phase HTTPS webhooks with private/loopback/link-local/CGNAT/ULA IP blocking, DNS-pinned connections, optional `PREMIER_ROTATION_ALLOWED_HOSTS`, and `PREMIER_ROTATION_*`-only env signing-secret fallback (`prepare` → vault write → `commit`, restoring the prior value and sending `rollback` on commit failure), producing audit receipts that never record secret plaintext. One-click offboarding (`POST /v1/security/offboard` / `premier auth revoke`) disables or deletes the account case-insensitively, revokes browser sessions, access tokens, SSH keys, JIT grants, live agent sessions, and OIDC workload tokens, and dispatches rotation webhooks (or records manual-revocation items) for secrets exposed across any branch/ref across every loaded repository in the registry.

**Commits are judged on the branch that shows them.** Path rules can differ per branch. The commit list and a commit's patch are filtered by the rules of the branch through which the caller can see that commit, not by the default branch's. A commit reachable from several visible branches is shown if one of them lets the caller list a file it changed, and its hunks follow that same branch's rules.

**Identity comes from the server.** Who you are comes from your session or token. Which groups you are in comes from the server's directory. A request cannot claim either. Only owners can view as someone else.

**Unknown repositories and hidden repositories look alike.** A caller who can see nothing in a repository gets the same "not found" as for a name that does not exist.

**Imported policies are not trusted.** A policy file that arrives with an imported repository is held back until an owner reviews and applies it.

**Administration needs a browser session.** Every action only an owner may take is refused to an access token, an owner's included: the policy, secrets, deciding agent approvals, starting agent sessions and committing or discarding them, budget approvals, KMS migration and DEK rotation, secret rotation webhooks, offboarding, publishing, branch visibility and deletion, overlays, the audit log, settings, backups, users, the directory and repositories. Owner-only and browser-only are declared in one place in the code, so a route cannot be one without the other. Account management and writes to `.access.toml` or `.env.schema` through the file API need a browser session too. Listing approvals and sessions (`GET /v1/approvals`, `GET /v1/agents/sessions`) is not administration and takes a token too: a member sees only their own, an owner all of them.

**The Git push exception.** Git has no browser session. An owner's access token can therefore push a commit that changes `.access.toml` or `.env.schema` on the default branch. Such a push is validated like a Studio save (it must parse, compile under the server policy and leave the owners in) and is written to the audit log with the account that pushed.

**Declassification firewall.** Every change that lands is scanned for leaks before any ref moves: a push (HTTP and SSH, commit by commit), a Studio save or delete, a publish, and a committed agent session. Everywhere it refuses content that holds a value from the server's vault (raw or in common encodings, matched by keyed digest, never stored in the clear) or a well-known credential pattern. Where the branch is readable by anonymous or signed-in visitors it also refuses restricted file names, configured sensitive identifiers, and snippets or whole files copied from restricted files, in file contents and in the commit message. An owner gets the full report; anyone else gets one generic rejection, whatever was found. An owner may override one blocking report from a browser session, if the server policy allows it, by naming that report's digest and giving a reason; the override is recorded and audited. An agent never can. `POST /v1/access/scan` and `premier access scan` run the same checks without landing anything.

**Active instruction quarantine.** Files that steer coding agents (`AGENTS.md`, `CLAUDE.md`, `.cursorrules`, `.cursor/rules/**`, `.github/copilot-instructions.md`, `.mcp.json`, `.claude/**`, `.github/workflows/**`, plus any the policy adds) are scanned for hidden Unicode, prompt-injection phrasing, shell exfiltration, credential access and unlisted egress hosts, and compared with any hash an owner pinned. Only an owner changes them (in the Studio, only from a browser session). A member's Studio edit is held for an owner's decision (`/v1/quarantine`) instead of being committed; a member's push, or an agent session, that changes one is refused, and no override lifts that for an agent. An agent session's workspace gets an instruction file only when it matches its pin and scans clean, or is exactly a version an owner approved; otherwise it gets the approved version, or no file at all, and the session log and audit log say which.

**No default branch, no trust.** A repository whose `HEAD` is detached has no default branch to take a policy from. The server then enforces the built-in owner-only policy, and judges every push under it, so only an owner can write anything, policy files included, on any branch. An empty repository is under the built-in policy too: its first push must come from an owner.

## Known limitations

Each of these is how the code behaves today.

### Deployment

- **No built-in TLS.** The server speaks plain HTTP. Passwords, tokens and code cross the network unencrypted unless you put an HTTPS reverse proxy in front.
- **Bind mounts must belong to uid 10001.** The container runs as a dedicated non-root user. A repository or state directory owned by anyone else, root included, does not work.
- **Without `--state-dir` the state is in the working tree.** A server started that way (a local checkout) keeps `.premier` and `.premier-local` next to the content. It never updates the working copy then, and reserved path components are still refused, but the separation is by name, not by place.
- **Lockout behind an unlisted proxy is shared.** Unless the proxy is named in `--trusted-proxy`, all users share its address: one person's failed sign-ins lock out everyone, and the session cookie is not marked `Secure`.
- **First run is open.** Whoever reaches a server with no accounts first creates the owner.
- **An owner has the run of the server.** An owner can change the policy and start agent sessions, which run commands on the host: confined where the sandbox works, as the server user where it does not. Treat an owner account as shell access.
- **The sandbox costs container hardening.** In Docker, bubblewrap works only with `--security-opt seccomp=unconfined --security-opt systempaths=unconfined`. That removes Docker's system-call filter and its masking of `/proc` and `/sys` paths for the whole container, the server included. Without the two options sessions are refused, unless you opt in to running without a sandbox.

### Data at rest

- **A backup holder can read all secrets in sovereign mode.** A backup contains the encrypted vault, the full unfiltered history, and, for the default repository, the password hashes, OIDC signing key, and two-factor secrets (and in sovereign `age` mode, `age.key`).
- **Sovereign `age` mode keeps its key next to the vault.** By default, sovereign mode stores `age.key` inside the state directory beside `vault.toml`. Configure Envelope KMS (`PREMIER_KMS_KEY`, an external `PREMIER_KMS_URI`, or HashiCorp Vault Transit) so the KEK is separated from the state directory.
- **Revocation does not reach existing clones.** Removing someone's access stops future fetches, and offboarding dispatches rotation webhooks for exposed secrets (flagging any without webhooks for manual rotation). What a user already cloned stays on their machine; rotate or replace any exposed secret lacking a webhook.
- **On Windows, state files rely on the directory's permissions.** Owner-only file modes are applied on Unix only.

### Policy

- **A policy change takes effect when it lands, with no second approval.** One owner committing `.access.toml` on the default branch changes the policy for everyone at once. The server checks that it loads and that owners keep the file; it does not check that the change is wise. An access token of an owner is enough to do it by `git push`, and only by `git push`.
- **A policy that stops loading keeps the old one, until a restart.** If a committed policy or schema cannot be loaded while the server runs (for example after the server policy changed), the previous one stays in force. A server that starts with a broken committed policy or schema does not start.
- **Owners are bound by the policy too**, but can change it.
- **Commit messages, authors and dates are not filtered, only scanned.** A commit that someone can see keeps its original message. The firewall refuses a message on a public or org-visible branch that names a restricted file or a configured sensitive identifier, quotes a restricted file, or holds a vault value or credential pattern. Anything else a message says about hidden work it cannot recognise, and authors and dates are not checked at all.
- **The file tree API reports `omitted_count` to owners only.** Members always receive `0` for `omitted_count` and never see omitted entry counts or names.
- **A taken branch name is a hint.** A member who tries to create a branch whose name is already used by a branch they cannot see gets a generic failure. That a valid name fails at all tells them something has it.
- **The firewall and the quarantine are static.** The firewall recognises copies of restricted content (whole files, names, and normalized snippets of at least `min_snippet_bytes`, 48 by default), vault values and known credential formats. Paraphrased, summarised, re-encoded, split or translated content is not caught, and neither is a secret that was never put in the vault and fits no known pattern. The quarantine matches patterns: an instruction that does harm in plain words it does not know passes, which is why agents only get pinned or approved instruction files. Approvals are by exact content: any change, even a harmless one, needs a new approval. A private branch is checked only for vault values and credential patterns, so restricted content can move between private branches freely until a publish or push crosses the boundary.

### Git

- **Force-push and branch deletion are owner- or personal-only.** Non-fast-forward pushes (`--force-with-lease`) and `git push --delete` both require strict compare-and-swap against the caller's projected tip and are permitted only for repository owners or on the pusher's own personal branch. The default branch can never be deleted, and a force-push always preserves the hidden files from the branch's current canonical tip untouched.
- **Tags follow anti-CFOR visibility.** Lightweight and commit-targeting annotated tags under `refs/tags/*` are advertised only when their target commit is already in the caller's projected history. Signed-in callers may push a new tag pointing to a commit they can see (or push in the same command), while updating or deleting an existing tag is owner-only with strict compare-and-swap.
- **Publish uses 3-way line-level merge and fails closed on conflicts.** When a regular text file with matching file modes changes on both the branch and the target, publish merges non-overlapping edits with `git merge-file` and checks the merged blob against private blobs before landing so a merge cannot reproduce restricted content. Overlapping edits, binary files, mode mismatches, and modify/delete collisions still refuse the entire publish; an owner is told the conflicting paths they may list, and how many others there are.
- **A member's publish preview can say "blocked" without saying why.** A member is given counts of what they are shown only: commits ahead, commits a publish would collapse, and no count of conflicts they may not list. The preview still says whether the publish would go through, so a refusal with no listed conflict tells them a hidden path conflicts.
- **Some ordinary pushes are refused.** If a branch gained commits you cannot see, a push that does not include the server's tip is rejected even when it looks like a fast-forward to you. Fetch, `git merge --no-ff`, and push again.
- **Pushes are buffered in memory.** Smart HTTP caps `git-upload-pack` fetches at 1 MiB and `git-receive-pack` pushes at 512 MiB. One push can hold up to 512 MiB of RAM on the server while it is processed, and the request is read before the push is checked against the policy.
- **Backups are built in memory**, so a backup of a large repository needs that much RAM.
- **Git over SSH is optional and strictly scoped.** When enabled (`--ssh-bind` / `PREMIER_SSH_BIND`), Premier runs a pure-Rust SSH listener with public-key-only authentication (password, keyboard-interactive, and `none` auth are rejected), a strict exec allow-list limited to `git-upload-pack` and `git-receive-pack` with sanitized repository paths, and interactive shells, PTYs, subsystems (SFTP), and TCP port forwarding refused fail-closed. Every SSH session uses the same server-side projection, policy, and overlay guard as Smart HTTP, with bounded request caps (SSH: 4 MiB `git-upload-pack` / 512 MiB `git-receive-pack`; Smart HTTP: 1 MiB `git-upload-pack` / 512 MiB `git-receive-pack`). When `--ssh-bind` is omitted or empty, only HTTP is served.

### Agent sessions

- **Egress is enforced only inside the sandbox.** When `/health` reports `agent_sandbox: "bwrap"`, a session has no network but a relay to its own proxy, and a connection that avoids the proxy has no route. Without the sandbox (`--allow-unsandboxed-agents` on a host where bubblewrap does not work) the proxy is only set through `HTTP_PROXY` and `HTTPS_PROXY`: an agent that ignores those variables can connect directly, to anywhere.
- **An allowed host receives whatever the agent sends.** The proxy decides where a request may go, not what it carries. An agent can send any file it can read to a host its profile lists under `allow_egress_hosts`, or to a host a secret's schema allows. It still has no secret values to send.
- **`premier agent run` is a weaker cage.** The CLI command runs an agent in your own checkout, not in a projected copy. The working directory is writable in place, and the policy hides no file from it. With bubblewrap, the rest of the filesystem is read-only, and only `.premier`, `.premier-local`, the vault, key and audit files, `/run/user` and a fixed list of credential stores in your home (`.ssh`, `.aws`, `.azure`, `.gnupg`, `.kube`, `.docker`, `.config/gcloud`, `.config/gh`, `.netrc`, `.npmrc`, `.git-credentials`) are masked; anything else in your home is readable. Its network is the proxy only, as in a session, unless the proxy's socket could not be created: then it keeps the host network and reports `cooperative-egress`. Without bubblewrap it refuses to run unless you pass `--allow-unsandboxed`; then only the environment is cleaned, and the agent can read every file you can and bypass the proxy.
- **The server checks who may write, and scans what was written; it does not review it.** An owner commits a session's change set as a whole. Policy decides which paths it may touch, the declassification firewall refuses leaks it recognises, and the quarantine refuses any change to an instruction file. Nothing judges whether the rest of the code is safe or correct. If the change set includes `.access.toml` or `.env.schema` on the default branch and passes the checks, committing it changes the policy. Read the change set first.
- **The agent can read the image's programs.** The sandbox shows `/usr`, `/bin`, `/sbin`, `/lib`, `/lib64`, `/etc/ssl`, `/etc/ca-certificates` and `/etc/alternatives`. Anything you install or copy under those paths, a credential baked into `/usr/local` for example, is readable by every agent. If the server user's home or a directory the server hides lies under one of them, it is emptied.
- **Without user namespaces the agent is the server's user.** Where the host forbids user namespaces, the sandboxed command runs as the server's user with every capability dropped, instead of as uid 1000 in a namespace. It still sees only the allow-list. A server that itself runs as root refuses sessions in that situation unless `--allow-unsandboxed-agents` is set.
- **OS resource caps and process suspension differ by platform.** Per-profile autonomy budgets cap files modified, lines changed, workspace bytes, egress requests/bytes, JIT requests, denied attempts, and session duration on every platform. On Linux/Unix, `setrlimit` (`RLIMIT_AS`, `RLIMIT_CPU`), best-effort cgroup v2 (`memory.max`, `pids.max`, `cgroup.freeze`), and unsandboxed `-pgid` `SIGSTOP`/`SIGCONT` process-group signals also apply. If writable cgroup v2 freezing is unavailable for a sandboxed `bwrap --new-session` session on Linux, pause breaches terminate the session instead. On Windows, the agent's process tree runs in a Job Object that enforces `max_memory_mb` (job-wide committed memory) and `max_pids` (live processes) and kills every process in the job when the session ends; `max_cpu_secs` and suspension are not available there, so a pause breach is enforced by the proxy (`429`) and the workspace checks. A Job Object confines processes only: it is not a filesystem or network sandbox.
- **Without a sandbox there is no isolation.** With `--allow-unsandboxed-agents` on a host with no working sandbox, the command can read and write everything the server user can, including the account file, the vault and its key, and its network is open.
- **Symbolic links are only partly carried.** A link whose target is absolute or leads outside the workspace is not put into it, and such a link made by an agent is not committed; it is listed as skipped. A session's commit is refused if it deletes or replaces a path that is a link in the server's working copy. A server on Windows puts no links into a workspace and cannot see an executable bit: files keep the mode the branch had, and new files are not executable.
- **Output redaction matches known encodings.** A secret is scrubbed from session output when it appears raw or percent-, hex-, JSON- or base64-encoded. Any other transformation of the value would not be caught, and values shorter than 4 bytes are not scrubbed at all.

### MCP gateway

- **`stdio` MCP servers run on the host outside the agent sandbox.** Although the gateway clears the child environment down to baseline OS paths (`PATH`, `TEMP`/`TMP`/`TMPDIR`, plus Windows system variables on Windows) and declared `env` / bound credentials, a local `stdio` server runs with normal host filesystem and network access. On `premier serve`, `stdio` servers declared only in repository `.access.toml` are disabled unless `--allow-unsandboxed-agents` is set or promoted to `--server-policy`; local `premier mcp gateway` trusts the checked-out workspace `.access.toml` and only spawns servers reachable by the active caller.
- **TOFU trusts the first clean observation unless a hash is pinned in Server policy.** When `pin_on_first_use = true`, clean tools allowed for the caller record a baseline hash; disallowed tools never create pins. Repository-layer `pinned_tool_hashes` still run poisoning heuristics and respect quarantine, whereas trusted Server-layer `pinned_tool_hashes` can explicitly override heuristic flags.
- **Poisoning heuristics are pattern-based, not semantic.** `scan_tool_poisoning` scans tool `name`, `description`, `inputSchema`, and `annotations` for hidden Unicode tag/bidirectional/zero-width controls and known prompt-injection markers, not arbitrary natural-language instructions or upstream runtime behavior.
- **Secret bindings require explicit server opt-in and `egress` alignment.** A secret without `mcp_servers` in `.env.schema` cannot bind to any MCP server, and secrets with an `[vars.<NAME>.egress]` section are rejected on `stdio` servers (`http_sse` only).
- **Agent JIT approvals require `premier serve` or server-scoped tokens.** `premier mcp gateway` refuses `--auto-approve-jit` whenever `--agent-profile` is set and otherwise fails `jit` tools closed over stdio. On `premier serve`, `/v1/auth/tokens` supports server-bound `agent_profile` tokens so delegated agents cannot widen or drop their profile via query strings or headers, and `/v1/mcp/rpc` binds JIT grants to canonical argument hash and ref.

### Imports

- **Import URLs are pinned to vetted addresses.** Before cloning, the server resolves the import host, rejects loopback, link-local, unspecified, broadcast, and (unless `--allow-private-imports` is set) RFC 1918, CGNAT and unique-local addresses, pins Git to those exact IP addresses via `http.curloptResolve`, disables HTTP redirects, and restricts `GIT_ALLOW_PROTOCOL=https`. Only owners can import.

### GitHub Companion

- **Staging isolation and outbound scrubbing.** Squash-Declassify PR publishing and outbound zone sync materialize commits inside a temporary bare repository that receives only vetted public blobs (anonymous `READ`, ancestor traversal, optional zone membership, excluding `.access.toml`, `.env.schema`, overlays, reserved components, and private-blob copies) and passes `git fsck --strict --full` before pushing. `sync-out` defaults to squashing (`squash: true`), enforces branch confidentiality (refusing non-public canonical branches with `403`), and explicitly non-squashed mirroring (`--no-squash`) still scrubs merge/revert/cherry-pick references and full canonical OIDs so private commit ancestry and canonical OIDs stay off GitHub.
- **Token storage and transport.** The GitHub token is encrypted inside the workspace `age` AEAD vault under an internal coordinate outside `.env.schema` and `SecretResolver`, so agent sessions and API responses never receive it. Changing the GitHub host drops any previously stored token. Git runs with `GIT_ALLOW_PROTOCOL=https`, `http.followRedirects=false`, and the `Authorization` header passed via `GIT_CONFIG_COUNT` environment variables rather than command arguments or remote URLs, and scrubbed from errors. Operations serialize across server and CLI processes via an OS file lock (`github-companion.lock`), and the `premier github` CLI enforces the committed `HEAD:.access.toml` together with `PREMIER_SERVER_POLICY` / persisted `server-policy-path.txt`.
- **SSRF and host pinning.** Connections default to `github.com` and `api.github.com`; enterprise hosts require explicit server allowlisting (`--github-enterprise-host`). Before every Git or REST call, the host is resolved, private/loopback/link-local/CGNAT/ULA/special-use IPv4/IPv6 addresses are rejected, Git is pinned with `http.curloptResolve`, the REST client connects directly to a vetted address over `rustls` TLS with redirects refused, and every `/v1/github/*` route requires an owner browser session.
- **Fail-closed inbound sync.** Upstream fetches enable `transfer.fsckObjects=true` and `fetch.fsckObjects=true`, and upstream commits are validated atomically across the entire incoming range before any canonical ref moves; commits touching `.access.toml`, `.env.schema` (including NTFS/HFS-folded aliases), restricted or out-of-zone paths, overlays, reserved names, `deny write` paths, case-colliding hidden or public paths, or unsafe symlinks/gitlinks are rejected without modifying canonical history, while hidden files remain untouched. As with local Squash-Declassify, attestation trailers do not verify upstream commit signatures (`sig=unverified`).

### Smaller points

- **A file can be swapped between check and open.** Mounting an overlay with a new file checks the working-copy path for symlinks before creating the file, not atomically. Something that changes the working copy at that moment, such as a push that moves the default branch, could exploit the gap. Reading and editing files in the Studio do not go through the working copy.
- **Not built at all:** lazy virtual filesystem enforcement and signed projection attestations in a transparency log. The [README](../README.md#designed-not-built) has the full list.

## Recommendations

1. Put the server behind HTTPS and list the proxy in `--trusted-proxy`.
2. Create the owner account before the server is reachable by anyone else, and turn on two-factor.
3. Keep the number of owners small.
4. Store backups as carefully as you would store the secrets themselves.
5. Check every rule with **View as** before you rely on it.
6. Do not run agent sessions on commands you do not trust unless the sandbox reports `bwrap`. Keep each agent profile's `allow_egress_hosts` short, and read a session's change set before you commit it.

## Reporting a vulnerability

Report suspected vulnerabilities in Premier privately, never as a public issue. [SECURITY.md](../SECURITY.md) describes how, and what response times to expect. Operators of self-hosted Premier instances should publish their own security contact and response SLA alongside their deployment documentation.
